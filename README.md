A production-oriented Python / FastAPI backend for the Banwee commerce platform. It provides account management, catalog and inventory operations, cart and checkout workflows, payments, orders, shipping, subscriptions, analytics, webhooks, and operational health endpoints behind a versioned `/v1` API.

## Service profile

- **Runtime:** Python 3.11+ with FastAPI and Uvicorn
- **Database:** PostgreSQL 14+ with SQLAlchemy async access
- **Migrations:** Alembic
- **Authentication:** JWT access and refresh tokens
- **Payments:** Stripe
- **Email:** Brevo-compatible email delivery
- **API contract:** OpenAPI 3, generated by FastAPI
- **Default local address:** `http://localhost:8000`
- **Test coverage:** ~97% line coverage across `api/`, `services/`, `core/`, `models/`, `schemas/`

## Architecture

Requests flow through three layers, each with a single responsibility:

```
api/*        HTTP routing, auth dependency, request/response schema validation
services/*   Business logic, transactions, third-party integrations (Stripe, Brevo, OAuth)
models/*     SQLAlchemy ORM models, one module per bounded domain
```

`schemas/` holds the Pydantic request/response contracts that sit at the `api/` boundary; `services/` never
returns a schema directly, keeping persistence and transport concerns separate. Domains are organized
consistently across all four layers: `accounts`, `catalog`, `commerce`, `analytics`, `system`.

The database is a single PostgreSQL instance split into Postgres schemas by domain
(`accounts`, `catalog`, `commerce`, `admin`, `system`, plus `public`) rather than separate databases,
so foreign keys can cross domain boundaries (e.g. an order referencing a user) while keeping each
domain's tables logically grouped.

Two categories of work run outside the request/response cycle:

- **`BackgroundTasks`** (FastAPI's built-in mechanism) for one-off, fire-and-forget work triggered by a
  request — sending a transactional email, updating a search index — that shouldn't block the response.
- **`core/worker.py`'s asyncio scheduler** for recurring jobs — subscription renewal/billing and
  promocode expiry — running in-process on a timer (no Redis, Celery, or external queue). Each job is
  also exposed as an admin-triggerable endpoint (e.g. `POST /v1/subscriptions/trigger-order-processing/`)
  for manual/ops-driven runs.

## Prerequisites

Install the following before setting up the service:

- Python 3.11 or newer
- PostgreSQL 14 or newer
- PostgreSQL extensions and schemas required by the active migrations
- Stripe credentials for payment workflows
- OAuth and email credentials when those integrations are enabled

## Local setup

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

Create `backend/.env.dev` for local development. The application also accepts `backend/.env` as a fallback.

```dotenv
ENVIRONMENT=dev
SECRET_KEY=replace-with-a-long-random-development-secret
DATABASE_URL=postgresql://banwee:password@localhost:5432/banwee
FRONTEND_URL=http://localhost:5173
DB_POOL_SIZE=10
ACCESS_TOKEN_EXPIRE_MINUTES=60
REFRESH_TOKEN_EXPIRE_DAYS=7
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
BREVO_API_KEY=
BREVO_FROM_EMAIL=Banwee <noreply@banwee.com>
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
FACEBOOK_APP_ID=
FACEBOOK_APP_SECRET=
```

The application converts `DATABASE_URL` to the async SQLAlchemy driver for runtime queries and to the synchronous PostgreSQL driver for Alembic migrations. Do not commit environment files or credentials.

## Database lifecycle

Run migrations from `backend/` with the virtual environment active:

```bash
alembic upgrade head
alembic current
alembic history
```

Create a migration only after reviewing the generated SQL and the affected model changes:

```bash
alembic revision --autogenerate -m "describe the schema change"
alembic upgrade head
```

For production releases, take a database backup, apply migrations before starting application workers, and verify `alembic current` after deployment. Never use `--autogenerate` as a substitute for reviewing a migration.

## Run the service

Development server with reload:

```bash
uvicorn main:app --app-dir backend --host 0.0.0.0 --port 8000 --reload
```

The repository helper can also be used from `backend/`:

```bash
./start-app.sh
```

Production processes should run behind a TLS-terminating reverse proxy or load balancer. Use a process manager or container orchestration platform to restart failed workers and keep secrets outside the image.

## API documentation

The canonical contract is generated from the application schema:

- Interactive Swagger UI: `GET /docs`
- ReDoc: `GET /redoc`
- Raw OpenAPI: `GET /openapi.json`
- Human-readable endpoint matrix: [`api.md`](api.md)
- Importable requests: [`postman_collection.json`](postman_collection.json)

All versioned endpoints use the `/v1` prefix. Set `baseUrl` and `accessToken` in Postman before sending requests. Protected requests use:

```http
Authorization: Bearer <access_token>
```

Regenerate the API artifacts whenever a route, schema, or authentication rule changes. The generated files must contain the same operation count as `app.openapi()` before release.

## Authentication and authorization

The authentication flow is:

1. Register or sign in through `/v1/auth/register/` or `/v1/auth/login/`.
2. Send the returned access token as a Bearer token.
3. Refresh short-lived access tokens through `/v1/auth/refresh/`.
4. Revoke refresh tokens during logout or account security events.

Use a unique, high-entropy `SECRET_KEY` in every deployed environment. Rotate signing keys through a controlled migration plan, invalidate compromised refresh tokens, and never log access tokens, passwords, payment secrets, or OAuth client secrets.

## Production configuration

At minimum, production must provide:

- `ENVIRONMENT=production`
- A non-default `SECRET_KEY`
- A private PostgreSQL `DATABASE_URL`
- A restricted `FRONTEND_URL` and corresponding CORS policy
- Stripe secret and webhook signing keys
- Email provider credentials for transactional mail
- OAuth credentials for enabled social login providers
- `DB_POOL_SIZE` sized for the database connection limit

Set `ALLOWED_HOSTS` in the deployment environment when host validation is enabled by the runtime configuration. Keep CORS origins explicit; do not use wildcard origins with credentials in production.

## Payments and webhooks

Stripe operations require server-side secret-key access. Webhook endpoints must validate Stripe signatures using `STRIPE_WEBHOOK_SECRET`, be reachable through the public ingress layer, and be safe to retry. Verify payment state from Stripe before fulfilling an order; do not trust client-submitted payment status.

Use Stripe test keys and test cards in non-production environments. Keep live keys in a managed secret store and rotate them without placing them in source control, logs, Postman exports, or issue descriptions.

## Testing and quality gates

This suite deliberately avoids mocking the code under test. Tests run against a real PostgreSQL
database (each test executes inside a transaction that's rolled back on teardown, so nothing persists)
and, where `STRIPE_SECRET_KEY` is a real `sk_test_...` key, against Stripe's actual test-mode API —
not a mocked Stripe client. Only genuinely external boundaries with no usable test-mode sandbox
(e.g. a third-party carrier API, an OAuth provider's token endpoint) are faked, and only at that
exact boundary. This catches real integration bugs — schema/DB mismatches, Stripe response-shape
changes — that a fully-mocked suite would miss.

CI runs with a placeholder Stripe key, so Stripe-dependent tests are automatically skipped there
(see the `pytest.skip(...)` guard at the top of files like `tests/services/commerce/test_payments.py`).
Run those tests locally with a real Stripe test-mode key in `.env.dev` before merging any change
that touches payments, subscriptions, or refunds.

Run the full suite from `backend/`:

```bash
source .venv/bin/activate
pytest
```

Useful focused checks:

```bash
pytest tests/api tests/services
pytest tests/models tests/schemas
python -m compileall -q api core models schemas services tests
pytest --cov --cov-report=term-missing   # coverage.py needs the dotted-module form for --cov=path,
                                          # e.g. --cov=services.commerce.payments, not a file path
```

Before merging a backend change, verify migrations, authentication behavior, idempotency for payment and order workflows, error responses, and the generated OpenAPI contract. Keep generated coverage files out of commits. CI enforces a minimum coverage floor (`--cov-fail-under` in `.github/workflows/ci.yml`) — raise it further rather than lowering it if coverage improves.

## Observability and operations

- Monitor `/v1/health/` and the root service endpoint through the deployment health system.
- Capture structured application logs with request correlation and deployment metadata.
- Alert on elevated `5xx`, database connection failures, payment webhook failures, queue or scheduler failures, and authentication spikes.
- Track latency and error rates by route, status code, and dependency.
- Keep application logs free of credentials, authorization headers, personal secrets, and full payment details.
- Use graceful shutdown so background schedulers and in-flight requests can finish cleanly.

## Troubleshooting

**The service fails during startup.** Check `ENVIRONMENT`, `SECRET_KEY`, `DATABASE_URL`, PostgreSQL availability, and migration state. Production startup rejects the default secret.

**Requests return `401`.** Confirm the access token has not expired, uses the `Bearer` scheme, and was signed with the active environment secret.

**Requests return `422`.** Compare the payload with the request model in `/docs` or the matching operation in [`api.md`](api.md).

**Payment state is inconsistent.** Inspect Stripe event delivery and signature validation, then reconcile the server-side payment record with Stripe before retrying fulfillment.

**Database connections are exhausted.** Review `DB_POOL_SIZE`, worker count, connection limits, and long-running transactions before increasing the pool.
